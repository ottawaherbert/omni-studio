# 全案蓝图：维度、创作支撑与优化建议

日期：2026-09-29。范围：截图中的全案蓝图及其四个分区。依据为当前工作区（HEAD `c78bea4d`，包含已有未提交修改），不是只看提交版本。

本报告第一至七节保留实施前的审计结论。当时仅调研、检查和形成报告；用户随后授权的实施结果见第八节。大纲、分场、写作页面的完整审查留到各自模块；这里只检查它们能否拿到蓝图资料。

## 一、结论

**四个分区的基本划分成立，适合作为创作起点，无需推翻或增加主流程。现有资料也能支持基本创作，但目前还不能认定这些资料会被所有后续 AI 入口稳定使用。**

需要分开看两个问题：

1. **内容维度是否合理：**大部分合理。创作方向、人物、故事世界、作品形式已经覆盖主要基础。部分字段含义混在一起，少数有用字段没有展示。
2. **资料是否真正服务后续创作：**存在明确缺口。当前聊天与生成读取的资料不一致；既有人物、设定也缺少对应的 AI 定向修改操作。

| 分区 | 判断 | 建议力度 |
| --- | --- | --- |
| 全案总览与主线 | 构想与大纲衔接合理；主题、冲突、风格要求的归属不够清楚 | 小幅整理，利用已有字段 |
| 登场人物小传 | 目标、内在需要、说话方式有用；尚不足以完整表达“这个人是谁” | 补一个可选简介，展示已有的可选人物维度 |
| 故事设定 | 分类、自由文本、适用范围、确认状态基本够用 | 保留结构，优先修复读取与修改衔接 |
| 项目体裁与规格 | 组织形式、跨集关系、集数、时长已经较完整 | 保留，调整主次，处理未确认默认值 |

“能生成内容”不等于“始终遵守全部资料”，也不等于创作品质已经验收。

## 二、资料参考与使用边界

Screen Australia 的《Story Documents – Drama》区分开发阶段与制作阶段的 Bible，涉及构想、主题、人物、世界和作品形式，并强调内容可随项目变化；人物也不必一律完成成长转变。它适合作为覆盖面参考，不能直接变成我们产品的必填表。[指南第 11–12 页](https://www.screenaustralia.gov.au/resource/story-documents-drama-2/)

John August 针对人物失去方向的问题，强调还需要知道人物在故事中做什么。这支持在人物资料中保留行动目标，但不能据此要求所有作者在蓝图阶段确定完整结局。[Story first, then characters](https://johnaugust.com/2003/story-first-then-characters)

下文的字段安排和开发优先级是结合本产品的判断，不是行业统一标准。我们的蓝图是持续更新的创作依据，不承担完整提案书、剧集制作手册或拍摄计划的全部职责。

## 三、分区审查

### 1. 全案总览与主线

#### 当前实际内容

- 故事想法与前提：`brief.concept`。
- 主要问题或冲突：实际保存为 `brief.theme`。
- 故事总纲与分集大纲：展示已有总纲预览，跳转到大纲页；此处没有重复编辑一份大纲。
- 数据中另有 `audienceExperience` 和 `constraints`，当前蓝图页面没有相应编辑入口。

证据：[总览页面](/Users/yang/Desktop/code/movie/a-22/apps/web/src/features/script/components/StoryBibleView.tsx:363)、[主题字段](/Users/yang/Desktop/code/movie/a-22/apps/web/src/features/script/components/StoryBibleView.tsx:410)、[数据定义](/Users/yang/Desktop/code/movie/a-22/packages/script/src/schema.ts:62)。

#### 判断

构想加主题足以起步，总纲留在后续页面也正确。应保留这个边界。

“主题”和“冲突”相关，但回答的问题不同：冲突说明人物面对什么阻力、压力或关系问题；主题说明作品关注什么问题与意义。目前生成合同容许“主题或主要问题”，所以不是字段必然写错，但入口会让用户把两者及创作风格都塞在同一处。

对当前以 AI 协作为主的创作方式，**风格观感与作者要求需要有稳定、可查看的归属**。例如“不要过度伤感，主角更主动务实”，后续应能持续读取，不能只依赖用户记得在哪次聊天里说过。

#### 有限优化方案

建议分区名为“创作方向与概览”，内部保留以下内容：

| 内容 | 作用 | 处理建议 |
| --- | --- | --- |
| 核心构想 | 主要人物或群体、处境、行动方向、主要压力与利害 | 保留 `concept`，用提示语帮助组织一段话；不拆成五个必填框 |
| 主题与核心问题 | 想探讨什么，可以暂时没有结论 | 保留 `theme`，明确可选；具体行动冲突可在构想中说明 |
| 风格与观众感受 | 希望偏轻松、紧张、荒诞、温暖等何种体验 | 展示已有 `audienceExperience`，允许自由表达 |
| 作者要求 | 明确保留、避免的方向，必要的创作或制作限制 | 展示已有 `constraints`，可选 |
| 已有大纲预览 | 查看当前进展、进入大纲页 | 保留；不要求蓝图阶段完成大纲 |

连续剧可在构想里补充“为什么能持续发生故事”；单元剧可记录常驻关系及各集事件来源。不为这些情况再增加独立强制模块。

如果展示两个已有字段，必须同时打通聊天识别、候选生成、定向采用和后续读取。当前 Agent 共享字段白名单只有 `concept/theme/outline`，只增加输入框无法满足 AI 协作需求。[范围定义](/Users/yang/Desktop/code/movie/a-22/packages/script/src/agentScope.ts:16)

### 2. 登场人物小传

#### 当前实际内容

页面支持姓名、适用范围、人物目标、内在需要、说话方式。数据结构还存有 `contradiction`、`arc`，当前人物卡没有展示它们。导航写着“目标 · 经历 · 声音”，但没有独立的经历字段；“声音”实际是语言表达方式。[人物页面](/Users/yang/Desktop/code/movie/a-22/apps/web/src/features/script/components/StoryBibleView.tsx:482)

人物的 AI 图标目前带入“提供行动或对白选择”的讨论要求。它不等同于修改这名人物资料的指令。[图标行为](/Users/yang/Desktop/code/movie/a-22/apps/web/src/features/script/components/StoryBibleView.tsx:646)

#### 判断

目标、需要、说话方式应保留，能帮助写行动和对白。

主要不足是**身份、当下处境、影响选择的经历没有清楚的位置**。用户只能塞进姓名、说话方式或其他设定。这样能存文字，但容易让“说话方式”实际变成人物杂项简介。

同时，数据里已经存在的人物矛盾和变化方向可能影响模型，却不容易在人物页面核对。应先让已有内容可见，不需要再发明复杂的人物评分。

#### 有限优化方案

- 分区名可简化为“人物资料”；导航提示改为“身份 · 动机 · 表达”。
- 建议增加一个可选“人物简介”，自由描述身份、处境、性格表现及与当前故事相关的经历；不拆成年龄、职业、童年、星座等大量固定栏目。
- 保留人物目标、说话方式；将内在需要、已有矛盾和变化方向作为可选补充，已有内容不能隐藏得无法发现。
- 变化方向允许不变、反复、退步或待定，不要求每个人物必须成长。
- 人物关系继续由故事设定承载，不维护第二份独立关系事实；后续有真实需求再考虑关联显示。

**AI 协作还需要补齐针对已有角色 ID 的修改候选。**当前正式操作只有 `add_character`，没有更新既有人物的等价操作。已有角色卡可手动编辑，但不能把“AI 会讨论”当作“讨论后可直接采用到这个角色”。同样不能通过再新增同名角色来替代修改。[操作清单](/Users/yang/Desktop/code/movie/a-22/packages/script/src/agentScope.ts:7)

### 3. 故事设定

#### 当前实际内容

预设标签为地点、人物关系、社会环境、规则、关键事件、其他，支持自定义标签。每条设定有正文、适用范围、待确认/已确认状态。标签保存在文本中，不是独立的复杂实体系统。[标签](/Users/yang/Desktop/code/movie/a-22/apps/web/src/features/script/components/StoryBibleView.tsx:25)、[设定编辑与状态](/Users/yang/Desktop/code/movie/a-22/apps/web/src/features/script/components/StoryBibleView.tsx:747)

#### 判断

**这部分内容维度基本够用，暂不需要重做。**年代、地点、组织、关系、能力限制与代价等都可用现有文本和自定义标签表达。普通现实题材不需要填写完整世界观。

需要明确两项含义：

- “已确认设定”表示作者选定的创作依据，不代表某事件已经在剧本正文发生。
- “关键事件”可能是背景事实，也可能是计划。未来剧情应以大纲、分场为主，不能因为放进设定就当作历史事实。

首页蓝图和 AI 新增设定目前会保存为 `draft`。这是保守处理，不是数据丢失；但回复里写“已确定”的内容也可能仍显示“待确认”。整份蓝图采用又可能包含开放问题，因此不能简单把整批设定全部改成已确认。[首页保存](/Users/yang/Desktop/code/movie/a-22/packages/script/src/creation.ts:74)、[AI 新增设定](/Users/yang/Desktop/code/movie/a-22/packages/script/src/agentDraft.ts:182)

#### 有限优化方案

- 保留现有分类、自由文本、适用范围和两个确认状态。
- 作者明确决定的内容与 AI 候选应在聊天采用时正确落到对应状态；含糊或开放的内容继续待确认。不要要求用户做后台记忆维护。
- 补齐针对已有设定 ID 的修改候选，保留原有采用与版本保护。
- 最优先是让聊天、生成和 Agent 稳定读取设定及状态，见第五节。

本轮不建议另建地点库、组织库、规则引擎、关系图谱和必填世界观问卷。

### 4. 项目体裁与规格

#### 当前实际内容

已有作品类型名称、单部/分集、跨集关系、目标时长、计划集数、题材、画幅。跨集关系支持连续故事、常驻人物单集故事、独立故事合集、混合结构。

默认每集时长会更新仍沿用原默认值的单元，已经单独调整的单元不随之覆盖。计划集数和实际已经写出的集数分开。这些设计应保留。[规格页面](/Users/yang/Desktop/code/movie/a-22/apps/web/src/features/script/components/StoryBibleView.tsx:968)

#### 判断与建议

这部分对创作组织的支撑较完整，主要调整主次即可：

1. 可改名为“作品形式与篇幅”，导航提示为“形式 · 题材 · 集数与时长”。
2. 主要展示作品形式、题材、单部/分集、集数与目标时长；跨集关系仅在分集时强调。
3. 画幅放到可选制作设置，保留已有值。画幅对制作有用，蓝图阶段不应把它排在故事形式之前。
4. 数据里的语言、制作方式会进入部分生成请求，但蓝图规格页没有编辑入口。当前创建默认中文、真人实拍；使用动画等形式时，应能修改或明确其暂定性质。时长偏差、计入片头片尾已有专门时长功能，本页无需全部展开。

有一项比排版更重要：**尚未确定的作品形式、篇幅会得到默认值。**首页没有明确形式时可落到自定义单部、30 分钟；这些数值随后又是实际生成依据。应在开始大纲前让当前形式与篇幅容易被看见，并在确实存在歧义时由助手做一次针对性确认，避免无声地把默认值当成作者决定。无需增加长问卷。[默认值](/Users/yang/Desktop/code/movie/a-22/packages/script/src/creation.ts:6)、[蓝图解析](/Users/yang/Desktop/code/movie/a-22/packages/script/src/ideation.ts:63)

## 四、建议保留的结构与完成边界

建议仍保留四个分区：

1. 创作方向与概览。
2. 人物资料。
3. 故事设定。
4. 作品形式与篇幅。

蓝图可以进入大纲的实用条件是：作者已经有一个愿意展开的方向；主要人物或群体及其处境足够支撑当前任务；影响本次故事的关键规则有初步依据；作品形式和当前篇幅有可使用的选择或明确暂定值。

这不是新的硬性校验表。主题、配角、背景细节、人物弧线均可继续补充。系统当前“资料填写”已经声明不必填满，不应将它升级为艺术质量评分或阻挡入口。[当前提示](/Users/yang/Desktop/code/movie/a-22/apps/web/src/features/script/components/StoryBibleView.tsx:350)

大纲负责具体事件与因果，分场负责场景呈现，正文负责动作对白。蓝图不提前要求完成这些内容。已有上游改动提醒下游复核的机制也应保留。[复核机制](/Users/yang/Desktop/code/movie/a-22/packages/script/src/workflowReview.ts:14)

## 五、真实衔接检查：存在的功能缺口

### 5.1 隔离检查结果

使用内存 SQLite、真实 `createScriptAgentHost` 和 worker 创建隔离稿，向各资料字段放入不同标记；捕获普通聊天请求后回填固定 `CALL scene_body`，再捕获实际正文候选请求。未返回创作正文、未采用候选、未调用外部模型。另对照旧入口的 `buildScriptTaskContext`。

测试无历史对话补充、未选择 Skill，用于检查每个入口是否直接读取保存的资料：

| 资料标记 | 当前普通聊天请求 | 当前正文候选请求 | 旧生成上下文 |
| --- | --- | --- | --- |
| 构想、主题、总纲 | 未包含 | 包含 | 包含 |
| 观众感受、作者要求 | 未包含 | 包含 | 包含 |
| 人物姓名 | 包含 | 包含 | 包含 |
| 人物目标、矛盾、变化、说话方式 | 未包含 | 包含 | 包含 |
| 已确认设定文本 | 包含 | 未包含 | 包含 |
| 待确认设定文本 | 包含 | 未包含 | 包含 |

进一步源码检查：当前普通聊天的设定投影还去掉了 `status`；当前生成能力没有把本作品 `facts` 列为基础上下文。连续 Agent 的决策索引也未直接包含完整人物与设定，写作能力沿用同一套候选生成器。

- [当前候选生成投影](/Users/yang/Desktop/code/movie/a-22/apps/api/src/agent/scriptDraftCapabilities.ts:90)

历史对话、补充指令或辅助记忆可能偶然提供相同信息，因此不能断言每次生成都会违背设定。但这些来源不足以保证拿到最新蓝图；已保存资料应有稳定的直接读取路径。增加更多字段也不能自动解决这个问题。

### 5.2 采用与修改范围

当前 AI 能生成构想、主题，以及新增人物和设定；正式候选协议没有修改既有人物/设定的操作，也没有修改 `audienceExperience/constraints` 的操作。

这不影响页面已有手动编辑，却影响用户希望的“讨论修改后，采用到对应资料”。这属于蓝图创作闭环的实际缺口，不应通过修改按钮文案来宣称已经支持。

后续方案应以已有实体 ID、明确字段和版本为目标，沿用候选比较、采用、并发保护；不做无界覆盖整份蓝图。

## 六、原定实施顺序与验收条件（落实情况见第八节）

### A. 优先修复资料读取一致性

在普通聊天、单步生成和 Agent 的相应阶段中，统一提供本次范围内的创作依据：构想、主题、风格要求、作品规格、完整相关人物、设定与确认状态。保留跨集隔离和正文读取边界，不能为了补资料把其他独立故事正文全量塞入。

验收：隔离资料的标记能在应读取的请求中找到；待确认设定状态保留；无关独立集资料不进入；保存后读取新版本；不依赖额外选择 Skill。

### B. 补齐蓝图资料的定向采用

支持修改既有人物和设定；新展示的风格、作者要求也能经聊天生成候选并采用。明确要求确认某设定时可处理其状态，未决定的内容继续保留不确定性。

验收：修改原 ID 的目标字段，不重复新增人物，不覆盖无关设定；采用后页面与刷新后的数据一致；版本冲突保护继续有效。

### C. 进行有限字段与文案整理

展示已有风格/作者要求；增加一个可选人物简介并展示已有矛盾与变化；简化四个分区命名；将规格按写作需要排列，显示当前采用的形式与篇幅。新增字段必须覆盖保存、旧数据兼容、模型输出和采用全过程。

验收：可以留空；已有作品打开不丢字段；作者能核对 AI 实际使用的重要资料；正常进入大纲不被新增表单阻挡。

完成 A–C 后即可结束本模块优化并进入实际创作验收。关系图谱、人物评分、完整制作 Bible、额外强制阶段、固定结构问卷均不在本次建议范围。
