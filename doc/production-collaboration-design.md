# 制片协作与交接改造方案

日期：2026-11-02。状态：既有协作改造与本轮质量依赖规则分别记录；下文历史验证不代表本轮或具体作品验收。

本方案覆盖剧本交接、导演筹备、资产、可选三维制片、分镜、生成、声音、剪辑和审片。目标是让人和外部 Agent 使用同一份制作依据，快速完成整场作品，并能定位跑偏发生在哪里。

核心做法：把专业决定写入已有业务对象，交接随正常保存和采用完成；下游按当前用途读取与核对。保存草稿允许不完整；正式推进遵守当前质量阶段，缺检查、未通过或相关来源变化必须停止其依赖流程。一般创作建议和审美分歧不单独变成审批关卡。

本方案不启用内部自主助手，不恢复十二部门逐一审批，不新建通用流程引擎。实施入口以 [外部 Agent 手册](agent-guide.md) 为准。

已实现共享场面依据、基础导演方案、专业需求与节拍引用、事件状态、资产拍摄用途、实际观察、工作交接记录、固定素材剪辑片段及声音锚点。人类界面与外部Agent使用相同业务保存规则；场次、镜头、协作、剪辑、资产用途和3D增量编辑无需手动传技术版本号。旧全量接口与固定素材/导出合同保留后台防覆盖与真实来源检查。

普通分镜与提示词制作默认一次模型调用，不再自动追加评分与多轮修复；额外的批量artifact审计只在明确选择的专门路径使用，当前质量阶段依赖用于普通正式制作。上下文读取不会调模型、渲染或追加检查。实现保留既有候选、历史、用户暂停和正式采用。

实现选择复用 productionBasis、现有来源摘要和素材引用，没有另建usedSources账本或通用工作流。首版剪辑是按片段顺序排列的连续时间线，位置自动计算；不包含空隙轨道、完整骨骼/物理或专业NLE的全部功能，这些仍属原方案范围之外。工程验证使用隔离作品及本地合成测试媒体，不能替代青云宗布景或最终影片的作者验收。

## 当前质量依赖原则（2026-11-02）

[制作质量流程](production-quality-workflow.md)是当前推进规则：总导演负责全局创作，制片统筹负责推进，各专业执行实际检查，可同人或同Agent兼任，不内置自治多Agent。先全剧/整场总体，再拆镜，落实资产布景群演与按需3D，随后整组画面、实际视频声音，最后整场与整集回看。固定8阶段不是8次用户审批。

每次inspection冻结当前实际内容和媒体，逐criterion明确观察与通过/失败；未通过不得进入依赖下阶段。相关变化只失效相关检查，旧稿、失败候选、已有媒体和在途任务保留，不重发、不自动补通过，人无需手动管版本。上限沿用制作约定/workRecords，系统不自动发起重生成；达到上限停止该项及依赖，继续无关范围。普通制作保留，3D可选；选择previs须实际发送本镜构图，视频须实际使用visuals已审图。scratch仅实验。

保存草稿和合成预览不等于放行；quality/deliveries回取实际已整集总检的视频，不重编码另一份。生成preflight/submit/dispatch/import核验相应前置条件。代码不能证明评语诚实或画面一定好，责任人须在当前真实图声上判断。既有自动QA和批量artifact管线不能替代这套实际检查。

## 1 目标与边界

### 1.1 制作结果

- 一场戏的目的、空间、表演、物件状态、声音和剪辑相互支持，关键事件得到表达。
- 复杂布景在精建之前试人物、机位、道具和光线；远景、中景、近景来自同一可信环境。
- 上游改变时，下游知道具体受影响的内容，保留无关成果。
- 快速得到可看的整场粗剪或约定的阶段成果；有限粗审后交作者精审。
- 同一任务由人或外部 Agent 接手，都能找到当前依据、已有成果、实际问题和可继续的工作。

### 1.2 速度与复杂度

人和 AI 均不手动管理技术版本。页面不展示内部修改序号，正常编辑工具自动携带必要保存标记；后台只用它防止旧内容覆盖新修改。系统不新增分支、发布版本或逐阶段确认最新版本的流程。

普通编辑不因无关改动使全场失效。异步生成的旧输入结果保留为候选，不自动覆盖当前采用。确有写入冲突时保留待保存内容并指出影响，避免循环刷新或重放；后续优先缩小保存范围。已有媒体历史和防覆盖标记继续由内部管理，AI 通过编辑工具使用当前对象即可。

- 简单场次允许一次提交场面方案和镜头，不先办齐筹备手续。
- 保存草稿不要求创作字段齐全；阅读上下文不调用模型、不渲染、不自动检查全项目。
- 交接检查与执行者已有的看图、看片合并，不额外增加“发送、接收、批准”三次操作。
- 不变的来源与用途不重复检查；已查看结果再次打开不再记作新待审。
- 系统不因低评分、缺备注或仍有建议而自动重试生成。
- 普通制作和可选严格批量流程保持分开；3D 只在作品需要时使用。

### 1.3 本次不建设的能力

不建设通用工作流 DSL、部门 Agent 调度平台、全局事件总线、全项目审批图、自动审美打分器、无限自修复管线、刚体物理引擎或完整数字演员系统。不以此次改造为由更换生成核心、供应商、页面风格或项目存储架构。

## 3 工作组织

### 3.1 一条制作流程，按任务选择工具

```mermaid
flowchart LR
    A[剧本与作者要求] --> B[本场目的与事件设计]
    B --> C[联合筹备与必要试验]
    C --> D[资产与镜头方案]
    D --> E[按能力组织生成或导入]
    E --> F[整场剪辑与声音]
    F --> G[有限粗审和作者精审]
    C --> H[可选三维勘景与排演]
    H --> D
```

图表示信息流；正式推进另遵守顶部固定8阶段，不是七次批准。简单戏可在同一次编辑中完成 B、C、D。复杂动作可以先用已有模型试验，再细化资产。发现问题时按问题归属修订；不会自动从末尾返回剧本重跑全部步骤。

### 3.2 专业职责

| 职责 | 决定什么 | 交付到哪里 |
| --- | --- | --- |
| 导演 | 叙事目的、观众知情、人物关系、揭示时机和整体节奏 | 场导演方案与镜头意图 |
| 制片统筹 | 当前范围、顺序、可用资源、制作约定；确保必要交接有人执行 | 项目约定与现有任务 |
| 副导演、群演协调 | 按事件落实本场在场人员、入退场、站位、活动、人数规模与镜头禁入区；区分主角、剧情群演和环境人群 | 既有场次需求/事件状态及3D objects/frames；静态布置也适用 |
| 摄影与灯光 | 景别、构图、机位运动、光源动机及主次分离 | 镜头字段、空间方案与试拍 |
| 美术、置景与道具 | 地理、建筑功能、生活痕迹、尺寸和可操作部件 | 世界、资产、场次摆放 |
| 表演与动作 | 目标、反应、进入离开、接触、受力及动作可实现性 | 镜头调度与可选排演 |
| 服装与化妆 | 身份、故事日、外观变化、损伤和延续 | 现有资产外观与变体 |
| 场记 | 剧情状态、持物、位置、动作阶段和版本差异 | 场面连续性与实际观察 |
| 录音、声音与剪辑 | 对白、环境、画外信息、停顿、切点和声画关系 | 声音事件、音轨与剪辑片段 |
| 剧务与资源管理 | 当前制作所需人物、布景、道具和资源是否可用 | 资源引用、范围内缺项与任务安排 |

一人或一个外部 Agent 可以承担多个职责。只有工作量、专业需求和用户授权确有需要时才并行委派。角色标签用于解释决定来源，不形成独立审批权限。副导演/群演协调须由本次执行者明确承接，可以兼任；不能只在导演文字里提到群演而无人布置。

人员交接区分“本场有哪些人、当前事件谁在现场、当前镜头谁可见”。导演确定剧情依据，副导演/群演协调直接落实摆放，摄影看实际遮挡与规模，场记核对入退场及跨切状态，统筹汇合结果。静态试景可用人物代理，不依赖动画或视频；空场资产保持干净，但不能用空场图代替需要人物的场面验证。合理无人场不填人，不为流程另建审批、重复报告或自动返工。白模识别色按项目稳定使用：主要角色各自可辨，剧情群演与环境人群分别用不同色系并标注名称/活动；颜色仅供制作识别，不替代角色服装。

### 3.3 意见如何汇总

一次联合筹备直接形成采用的场面决定。只保留会影响实现的分歧，例如“池边窄道无法同时容纳苏晴介入与摄影机退移”；协调后把采用结果写到调度和布局中，不要求每个部门先出完整报告。

普通取景、摆放和实现取舍由当前执行者在授权范围内决定。涉及改写剧情、扩大成本、改变作者指定核心或覆盖作者锁定内容时，按原有权限处理。专业分歧本身不会触发全场暂停或自动多轮辩论。

## 4 交接规则

### 4.1 交接内容随作品保存

每次交接复用当前业务记录，包含：实际使用的来源、采用的制作决定、可使用的产物、已知影响与使用范围。系统可以从已有字段组成交接摘要，不要求手写另一份清单。

下游在使用这些内容时完成针对当前用途的核对。核对可以和看图、摆机位、编排镜头、制作粗剪合并；只有需要实际视觉证据的结论才关联图片或视频。普通文字方案不为“有证据”额外渲染。

| 交接 | 下游要读什么 | 最小工作与继续方式 |
| --- | --- | --- |
| 剧本到筹备 | 当前正文、作者要求、相关上游节拍与状态 | 保留原文，补当前需要的制作推断；无须先为全剧拆出所有字段 |
| 筹备到资产或布景 | 本场目的、关键动作、空间与取景要求 | 使用草模或现有素材试关键关系；简单场次可直接写镜头 |
| 布景到镜头 | 实际空间、资产用途、已查看机位和局部缺口 | 从本次会用的视角判断适用性；不要求整城所有区域完成 |
| 镜头到生成 | 动作、对白、估时、切点、边界状态与参考 | 使用当前生成预检；缺创作说明可提示，不触发补表循环 |
| 素材到剪辑 | 实际结果、技术状态、可用片段和明显问题 | 按约定粗审并先组整场；生成成功不自动标成作者认可 |
| 粗剪到作者 | 整场结果、已做检查、主要问题与采用情况 | 到约定交付点就交付，不为消除所有建议无限精修 |

### 4.2 三种问题处理

| 类型 | 例子 | 行为 |
| --- | --- | --- |
| 执行动作无法成立 | 必需引用不存在、容量超限、保存版本冲突、当前生成被作者暂停 | 只拦截对应保存、执行或采用动作；返回原因与可执行的修正入口 |
| 已证实影响当前用途 | 选中的白模参考明显穿模；所需动作缺失；人物身份错误 | 保留失败证据和草稿。当前材料不能标为该用途合格；在约定内修、换已有候选或留下缺口，其他工作继续 |
| 创作建议或未知 | 背景可能更丰富、节奏可能偏慢、某专业字段未填、没有精审 | 显示简短提示，允许制作；只有本次确实需要的信息才进一步处理 |

“可能不好”不能仅凭模型意见升级为服务端硬阻断。已证实的内容问题由有范围的实际观察记录，不依赖任意综合评分。已有版本保护、暂停、指定核心、媒体完整性和真实接触失败处理保持有效。

### 4.3 最少状态

任务沿用现有生命周期，参考和媒体沿用现有候选与采用状态。新增展示信息分为三个彼此独立的事实：

- 技术结果：是否保存、渲染、生成成功。
- 使用结论：尚未查看、适用于某用途、带已知问题暂用、该用途不适用。
- 作者决定：沿用正式采用者与采用记录，外部 Agent 的制作采用不显示为作者精审。

页面进度从这些事实推导，不再保存一个需要反复同步的“部门完成率”或“整城合格”状态。没有创作检查记录表示尚未评价，不会自动创建待审批任务。

## 5 数据归属与最小增量

### 5.1 保留唯一事实来源

| 信息 | 归属与变化 |
| --- | --- |
| 作者原稿与结构化交付 | 现有不可变交付快照；按 sourceWritingSceneId 解析，不回写作者稿 |
| 制片当前正文 | 现有 Scene.script / scriptBlocks；与作者快照有差异时明确显示 |
| 场次拆解 | 现有 Scene.breakdown；补可选节拍与来源定位，承载直接导入文本的制作拆解 |
| 叙事与专业决定 | 扩展现有 Scene.manualStoryboard.directorPlan，先保留存储路径，允许没有镜头时保存 |
| 空间与事件状态 | 现有 Scene.visualPlan；只补关键事件的状态变化，不重复角色档案 |
| 角色、服化与独立道具 | 现有资产和外观变体；尺寸、操作点按当前用途补充 |
| 固定世界与动态排演 | 现有世界、地点、模型、场次 objects / frames；剧情损坏不固化到空城原件 |
| 镜头作用与拍法 | 现有 Shot 的 motivation、editingNote、blocking、visualAction、continuityNote、directing 等 |
| 生成与候选 | 现有 task、plan、execution、result 和正式采用指针 |
| 观察与问题 | 扩展产物自身的 review；场面级观察存到 productionPreparation，统一只读汇总 |
| 剪辑 | 后续新增 Scene.edit 中的片段引用；旧 Shot 保持叙事身份 |
| 制作偏好与交付约定 | 现有 Project.productionWorkingAgreement 原文；不塞入画面来源摘要 |

### 5.2 场面方案

导演方案升级时保留 intent、rhythm、applications、exceptions 等现有内容，新增字段可选。基础方案不要求绑定 Skill；风格方法只作为额外来源。

实现结构重点如下，沿用项目既有 ID 和引用类型，不单独建立规则语言：

```ts
type BeatDirection = {
  beatId: string;              // 指向来源节拍或本场制作拆解
  intent: string;              // 此刻观众应得到的信息或情绪
  shotIds?: string[];          // 筹备阶段可以没有镜头
};

type ProductionRequirement = {
  id: string;
  department: string;         // 沿用既有专业角色目录
  description: string;        // 可执行要求
  reason?: string;
  beatIds?: string[];
  targetIds?: string[];        // 既有地点、资产、镜头等明确引用
};
```

方案按需带 beatDirections、requirements 和制作假设。最终镜头、布景和声音仍写在各自业务对象中；需求引用这些结果，不复制一套坐标、对白和素材地址。既有 applications 的方法落点继续保留。

上游节拍缺失时，执行者可从正文一次提取本次需要的关键事件，保存到制片拆解。系统不为每个句子强制创建节拍，不强制每镜绑定；空镜、反应镜头和过渡镜头仍可表达必要内容。

### 5.3 事件状态

在 Scene.visualPlan 里按需增加 eventStates，表示“哪个事件前后，哪些实体发生了什么变化”。只记录影响本场承接的变化，如佩剑在手到落地、山门完整到破损、竹枝在手到入池。

镜头可引用事件和节拍，具体姿态和变换仍在 Shot 与 previs 中。跨场连续性继续使用 entryState、exitState、transition。系统只做引用和明显结构冲突提示，不据文本相似度自动判断剧情错误。

### 5.4 实际观察

复用原审查者、时间、来源和结论字段，扩展可选 observations：目标引用、图片或媒体版本、时间段或机位、看到了什么、影响什么、建议修改哪个对象。场面级未归属问题存于 productionPreparation 的观察记录；具体产物的问题只保存在该产物 review，汇总页按引用读取。

观察可以是“低机位可用，未验证转身动作”，无需全部勾选。已有 needs_changes、technicalIssues 和接触失败结果仍是原始依据，不建立另一套可手工修改的通过标记来覆盖它们。

“带问题暂用”仅在作者约定允许、问题不触犯现有技术与内容底线时使用，沿用正式采用接口并记录审查者与局限；它是使用说明，不是绕过原有采用检查的新状态。

### 5.5 返工记忆

在现有 productionPreparation 中增加可选的本次范围工作记录：scopeKey、originTaskId、已执行粗审与返工摘要、最后动作和下一步。候选和执行次数优先从真实任务关系读取；人工或本地建模工作只补必要摘要。

这份记录帮助换会话后继续工作，不是额度授权表，也不会启动重试。返工次数、时间及暂用权限仍以真实制作约定为准；不把旧作品缺少字段解释成已获额外生成授权。

## 6 各模块的实现设计

### 6.1 剧本与制片交接

建立一个共用的场次来源解析函数，从当前制片正文、交付快照和已有拆解组成只读事实视图。作者包已有的目标、障碍、转折、表演要求、节拍和连续性进入该视图，保留来源定位。直接导入文本同样可以使用，不要求先经过写作模块。

制片正文已经修改时，旧快照只作为来源参考；与当前正文不再一致的结构化事实不能悄悄成为最新指令。用已有来源摘要标记需要核对的部分，执行者可在本次制作中修订相关拆解，不强迫重新导入全剧。制片采用的结构化修订仍属于制片副本。

只对本次范围展开完整正文与事实。世界总体规划可以读取全剧地点和事件摘要，并按需要展开相关场次；单镜任务不附带全剧所有部门报告。

### 6.2 导演与专业筹备

基础导演方案允许独立创建、编辑和保存，无需 Skill、镜头或专业评分。简单场次可以随镜头一次写入。已有导演 Skill 继续提供方法和风格，取消“未选 Skill 就不能形成基础方案”的耦合。

新的普通分镜任务在同一次返回中给出简短场面决定和镜头，保存后可供下游读取；依赖的正式执行须先通过对应质量检查。现有方案已经有效时只引用，不重写。返回遗漏部分创作说明时保留有效候选并提示具体缺项，不自动追加一轮模型调用来补表；外部 Agent 也可以在同一次作品保存中完成这些内容。

筹备默认回答四类问题：本场要表达什么、关键事件如何发生、空间与人物如何组织、哪些要求会影响后续制作。专业面板只展开当前需要的内容。完整专业目录可用于人工检查，但不会按缺少某部门的报告生成阻塞任务。

专业冲突在一个方案里解决，采用结果保留简短原因。方案变更同步修改真正受影响的镜头或需求引用；来源摘要由服务器生成，Agent 不自行宣称其他内容均未受影响。

### 6.3 资产与服化道

保留角色、场景、独立道具和声音资产的现有身份、参考和候选体系。增加可选的功能说明：适用景别、实际尺寸或尺度依据、必须可见或可操作的部位、当前已验证用途。只为参与取景或交互的资产填写。

三维资源的尺寸、挂点和结构以模型及现有空间合同为准，资产说明负责表达需要做什么。近景竹枝需要持握和可见轮廓，远处竹林可以简化；不能要求所有树木具备近景交互参数。

身份外观、剧情状态和场次摆放分开处理。山门破损、剑落地和服装损伤按事件变化，不覆盖原始空景与基础资产。服化变体继续复用现有外观和变体机制。

### 6.4 三维世界与布景

建城任务的输入增加相关场面要求、已有调度和机位意图。世界仍按整剧固定地理建设，场次只安排动态人物、道具和事件状态。新增剧集引用或扩建既有世界。

建设顺序为：总体地理与功能布局；关键动作和取景试验；主体结构；场次置景；按用途拍代表视角。步骤允许交错，已完成部分直接复用。全景地理可以先做低细节版本，同时精建主拍区域；环境不能在近景或反打中消失。

布局必须解释地点之间的联系、路径去向、标高、建筑用途与生活痕迹。美术细节根据人物身份和故事选择。影视城质量由这些关系及真实画面判断，不以对象数、建筑数或标签判断。

摄影交接保存已试的机位与焦距，区分“规划机位”和“实际拍过”。初版直接复用当前 camera、light、viewpoints、routes、objects 和 frames。复杂多灯、景深、完整骨骼、物理或导航只有在具体作品证明必要时单独立项，不作为本次协作系统的前置。

真实预览随当前世界/场次来源关联；关键接触使用现有 checks。静态参考不要求跑完整动态，动态参考按使用范围检查运动。允许保存和展示失败草稿；已发现明显穿模的参考不能当作合格材料送入后续生成，也不能以换机位掩盖问题。

渲染与导出复用 Three.js、现有 LOD、资源缓存、实例化、路径预载和后台任务。新的协作数据不进入每帧渲染循环，不要求每次打开场次重新建城或重拍。

### 6.5 分镜与生成单元

分镜读取本场事实、导演决定、连续性、相关资产和已验证空间。镜头的新增信息、切出条件、人物调度和边界状态继续写入既有字段。节拍与需求引用用于定位遗漏，不以“全部有引用”代替叙事判断。

叙事镜头、故事板画格、生成单元和剪辑片段保持不同身份。先按动作、对白、反应和切点估时，再按所选能力安排请求长度与参考数量；生成余量可以剪掉，不能通过缩短剧情来适配模型。

宫格和 3D 均按需要使用。需要 AI 联合宫格时遵循现有同次联合设计规则；静态检查拼图不能冒充联合生成。用户暂停模型或只要布景时，流程停在对应交付范围，不因“下一步推荐”启动生成。

### 6.6 生成、导入与候选

复用现有引擎，不新增生成前的部门批准层。预检把选定方案和参考固化到计划；执行保留已有版本、实际容量、核心与暂停保护。

提示词编译只带当前生成单元需要的内容，分开身份、环境、构图、动作、声音与风格用途。不能把资产白底要求带入剧情视频，也不把整份部门历史拼到提示词后面。

生成成功后记录技术结果，按制作约定看真实候选。观察直接进入既有 review，提供粗审范围、主要问题和可用片段；采用继续走正式接口。一个内容问题只指向受影响的候选、单元或资产，不触发全场自动重生成。

候选安排和已有在途任务共用计数。请求返回未知时查询原任务；不把重建任务或换种子当作不计数的新机会。技术故障恢复沿用现有处理，不新增供应商自动切换或多层重试包装。

### 6.7 声音与剪辑

对白表演和声音事件从导演方案、镜头与已有 soundCues 进入制作。事件应能表达动作声、环境变化、画外信息、声音先入和跨切镜延续；不强制每条声音恰好限制在单镜时长内。

Scene.edit 初版包含 clips，各片段保存稳定 ID、shotId、实际素材引用、sourceInSeconds、durationSeconds 和 timelineStartSeconds。素材版本与实际时长使用既有登记信息。一个镜头可对应多个片段，一个素材可多次使用；切分和修剪不再复制叙事镜头。

镜头预计时长、生成请求时长、实测素材时长和剪辑保留长度分别展示。素材被替换时，片段保持固定引用，提供明确的替换操作，不悄悄重绑当前采用结果。预览与导出使用同一份剪辑解析结果。

音轨沿用现有对象；按用途绑定场景时间、片段或对白。剪辑改变时，只对受影响的声音与字幕提示重定位，不能全场重配音。第一版不做全功能专业剪辑软件，优先实现片段拆分、修剪、排序、基础声画错位和正确导出。

### 6.8 互动作品

同一场面设计可供线性与互动制作使用，但分支事实按实际路径解释。汇合节点不能自动继承互斥分支里的全部物件状态。等待态时间不计作剧情节拍。

互动继续使用已有固定绑定和试玩快照。镜头或媒体修订后提示相关绑定可更新，由已有正式操作重建快照；不自动改写作者稿或发布中的体验。协作改造不要求普通线性作品具备互动结构。

## 7 人类界面与外部 Agent 接口

### 7.1 同一个场面上下文

扩展 buildProductionSceneContext，使筹备、建城、分镜和生成调用相同的纯数据解析。共享实现放在现有 production 服务层；渲染和生成仍由各自服务执行，不新增协调服务进程。

按目标返回：当前正文和相关事实、已采用的场面决定、连续性、直接相关资产与空间、实际成果索引、当前限制和简短下一步建议。重媒体与历史记录按需读取。

上下文区分事实、制作决定、假设、能力限制和实际观察。未实现的动作或灯光意图不能伪装成已执行。推荐动作只表示可做什么，GET 请求不会执行、采用或启动检查。

### 7.2 现有接口的扩展范围

| 现有入口 | 已实现扩展 | 保持不变 |
| --- | --- | --- |
| GET /api/operator/projects/:id/context | 增加范围内进度与当前约定的简洁摘要；提供场面上下文入口 | 不写作品，不扫描全部媒体 |
| GET /api/projects/:id/episodes/:epId/storyboard-team-context?sceneId=... | 返回统一场面上下文，供 UI 和授权外部 Agent 使用 | 保留原始来源与已有返回内容的兼容 |
| PUT /api/projects/:id/episodes/:epId | 保存新的可选导演、连续性、观察与剪辑字段 | 使用当前 productionRevision；保存草稿不要求各部门完成 |
| 建城 builds / build-contract | 冻结相关场面要求与实际来源引用；详情返回当前约定、候选、预览和问题 | 外部返回、本地编译、候选、修改、正式应用沿用现有流程 |
| generation context / workspace / plans | 使用同源场面决定，按目标编译；返回聚合的范围内提示 | 复用固定计划、已有执行与导入协议 |
| 现有结果 review / adopt | 可选结构化 observations，复用审查者与来源检查 | 不新建 review 后还要 approve 的第二次操作 |
| 现有预览、checks 与导出 | 关联实际使用范围和相同来源，向上下文提供索引 | 阅读上下文不触发这些重任务 |

世界或场面缺少现成 review 写入口时，在原领域保存接口上增加可选审查记录；若必须新增端点，跟随该领域命名及既有版本规则。实际接口已在手册和能力目录发布，不增加通用交接审批端点。

不新增 prepare / send / receive / approve / release 形式的五步协议。一次正式保存可以同时交付场面方案与镜头，一次正式采用可以同时记录已经完成的粗审。

### 7.3 下一步与错误返回

保留现有 code、message、blocking 和 allowedActions 习惯，补具体目标定位。一次返回只列对当前动作有影响的项；建议按必要性排序，不把所有历史警告铺给 Agent。

下一步可以是补一个必需引用、查看当前候选、修一个已确认问题、使用已有合适材料、继续另一场或交付当前结果。已达返工上限时不继续推荐重新生成。没有新增来源、观察或作者指令时，不把同一问题重新当作新任务。

### 7.4 人类操作体验

沿用现有筹备、资产、分镜、工作台与摄影棚页面。筹备中的“场次信息”展示本场目的、事件顺序和当前制作决定，专业内容按需展开。镜头、资产和 3D 检查器都能回看相关要求及修改依据。

当前页面优先显示作品和主要动作。问题放在相关对象旁边，提供直接跳转；不增加全屏审批向导、十二部门进度墙、嵌套表单或要求清空所有红点的首页。正常保存后可以直接继续下一项。

3D 工作区继续以场景为主体；可切实际机位和世界视角，代表预览显示来源与适用范围。生成工作台继续以参考、计划、候选和采用为主；技术成功与作者精审用准确文字区分。

桌面与窄屏沿用现有响应式布局、样式和图标。实现时验证关键操作可见、内容不遮挡、焦点与键盘操作可用，不为此次流程改造重新设计站点外观。

## 8 有限粗审与停止返工

### 8.1 工作安排

继续读取真实 productionWorkingAgreement。已有候选数、检查范围、轮数、返工或时间上限直接沿用。第一次涉及未约定的关键消耗或作者判断时合并询问；不在每个镜头重复问，也不因非关键缺项停掉独立工作。

新项目可向作者建议“一批一次粗审，明显问题至多一次定向返工，之后交付已有成果与问题”。只有作者采纳或已委托执行者决定，才记为本项目安排；这不是为旧项目虚构授权的全局默认。

修正后的结果只检查该问题和直接影响，不追加一轮全场精审。若约定不再检查或暂用未审素材，准确标记该状态，不能声称已粗审通过。

### 8.2 终止条件

出现以下任一情况，本轮不再自主追加同类返工：

- 已达到约定轮数、次数或时间。
- 当前问题需要系统尚未具备的能力、外部服务恢复或作者作决定。
- 已做修正没有提供新的可行方向，仅剩重复尝试。
- 剩余内容属于约定留给作者的精审或审美选择。

处理结果是保存成果、明确不能使用的部分与原因，交付可用部分，继续不受影响的工作。存在问题并不自动使项目整体进入 blocked；当前不可执行动作仍维持原有失败或等待状态。

### 8.3 避免循环的实现约束

- 不在保存、读取或模型回调后自动发起创作修复。
- 不存在 while 分数不足就再次生成的控制流。
- 换会话、任务 ID 或种子不清空已有工作记录；重新尝试仍属于原范围的返工。
- 同一来源、同一用途且没有新问题，不重复粗审。增加新的景别或动作属于新用途，检查只覆盖新增部分。
- 同一次修订合并相关问题一起改，避免按部门反复来回。
- 只有作者新增指令、放宽范围或出现新的有效实现路径时，才重新安排后续工作；不会把“还不完美”解释成继续授权。

这部分由简洁的操作规则、工作记录与下一步建议实现。首版不做新的额度账本、分布式租约或预算审批系统；现有生成幂等和队列不变。

## 9 来源变化与工程边界

### 9.1 有限依赖

按本次目标收集实际使用的正文、场面决定、资产、空间与参考。复用现有来源摘要机制，由服务端生成按目标的 productionBasis 与现有来源摘要。依赖以现有实体、版本和内容片段为单位，首版不建设通用依赖图数据库或对每句话计算语义影响。

| 变化 | 处理 |
| --- | --- |
| 修改制作约定、检查备注或无关资产 | 更新提示与工作安排，不作废画面或几何 |
| 修改本镜依赖的动作、对白或角色外观 | 相关计划提示来源变化；保留旧候选，更新本次计划后再执行或采用 |
| 改动洗剑池布局 | 相关场次的机位、调度与参考待核对；无关场次继续有效 |
| 改动当前世界但首版无法可靠定位可见影响 | 说明该世界范围需要核对，不自动重拍；执行者选择本次相关视角 |
| 新增一条负面实际观察 | 影响其明确指向的用途和产物；不使全部历史结果失效 |

世界应用继续遵守现有整份世界版本校验，不能因为想减少复核就忽略并发修改。首版不自动合并同一世界的冲突写入。旧候选可以查看和比较，不能沿用旧来源摘要覆盖新内容。

对已发生的相关变化，系统提供具体来源差异与修改入口。非相关字段从源摘要中排除；做不到精细判断时说明范围，不能假装所有引用都仍然有效。

### 9.2 检查放在哪里

- 外部输入在现有 API 边界做结构、归属与引用校验；内部服务使用已验证的领域类型，不逐层重复同一套 schema。
- CAS、来源、用户暂停和实际容量在原有执行/提交边界继续校验，避免长任务期间条件变化。它们与当前质量阶段检查并行，不能彼此替代。
- 创作字段缺少可编辑默认值时保留空值，不伪造“已确认”，也不以缺文字阻止草稿保存。
- 保留既有明确兼容格式；不新增多种猜测性字段解析、模糊 ID 匹配和静默供应商降级。
- 错误返回一次完整的相关问题，不使用嵌套重试、自动刷新后盲目重放、失败后偷偷换方案。
- 新增抽象必须解决至少两个真实调用方的重复逻辑；共享上下文确有多方使用，通用审批平台没有当前必要。

### 9.3 读取与运行效率

场面上下文读取不执行 ffmpeg、几何检查、渲染或模型请求。历史证据只读索引，展开时取媒体。单次请求内复用重复的来源计算；只有基准测试证明需要时才引入跨请求缓存。

一次场次任务原则上先取一份场面上下文，再按需要读取具体素材。可在一次模型或外部 Agent 返回中提交场面决定与镜头；不为十二个角色分十二次调用。文档和能力目录给出短入口，详细合同按领域展开。

渲染、导出和接触检查继续使用原后台任务与进度。等待在途任务期间不重新提交，也不高频轮询大上下文。没有新增重任务时，协作信息只增加少量字段解析与索引读取。

开发时记录同机、同数据范围的前后基准：上下文耗时及大小、完成一次简单交接的 HTTP 往返数、模型调用数、无变化重检次数。性能目标是普通路径不增加审批调用或额外模型调用；不以减少必要正文和素材信息来换取表面速度。

## 10 青云宗作品的完整示例

本节是改造后的使用示例，不代表已经修好现有影视城。沿用当前指令：只搭建并展示影视城；图片、视频生成模型不调用；白模视频待作者看后再做。

### 10.1 剧本事实与导演目的

四个剧本场景保留原场次身份，关联同一个连续发生的事件和宗门空间。导演意图是让林渊从边缘劳动者逐步成为全场视觉与权力中心，同时让苏晴的正直、赵恒的虚张声势和老祖的压迫可辨。

| 场景 | 必须表达的事件 | 对空间和布景的要求 |
| --- | --- | --- |
| 洗剑池冲突 | 挑水、踩柴、拔剑威胁、苏晴介入 | 洗剑劳动区、柴堆、赵恒进入路线、苏晴可介入的侧向空间，以及能看清三人关系的机位 |
| 山门受袭 | 防御破碎、弟子受压、老祖出现、赵恒退缩 | 山门与主拍区的空间关系、朝向天空的取景余地、群演与退路；破坏属于后续状态 |
| 一剑反转 | 林渊将苏晴带到身后、挡爪、万剑响应、斩开血云 | 人物前后转换、肩部接触范围、竹枝近景、仰拍背景与剑群的视觉空间 |
| 回归日常 | 众人拜服、竹枝入池、捡柴刀、走向茅屋 | 可理解的返回路线、池边投物位置、柴刀位置和能形成结束画面的茅屋方向 |

部分特殊动作超过现有代理能力时，先记录精细动作未验证。当前建城可验证所需空间，不为了补动作验收提前制作视频或调用生成模型。

### 10.2 联合筹备后的世界要求

主体拍摄区以洗剑池、劳动区、介入通道和开阔行动区组成；茅屋应符合杂役生活身份，与宗门大殿形成尺度和维护程度上的差别。周边补可信山路、台阶、排水、使用痕迹和符合宗门功能的建筑；远景表现山势、主峰、山门与天空关系。

摄影先试远景能否交代宗门与洗剑池，中景能否容纳冲突和保护动作，近景是否有可信的池沿、手持物和背景层次。美术根据试拍调整标高、开口与布景。场记记录剑、柴堆、竹枝、山门和人物状态的变化。

不预设固定镜头数量、统一焦段或统一时长。具体距离、坐标与细节密度由实际布局与取景决定；文档里的“有反打”“有远山”不能替代实际视角。

### 10.3 当前只建城的推进方式

1. 读取现有世界与四场剧本，保存本次场面要求和世界用途。保留原世界与候选。
2. 用已有模型或草模试空间及代表机位，在同一批工作中解决路径、尺度与前中后景。
3. 改造当前最影响取景的地形、劳动区、茅屋、道路和背景；按用途补结构与陈设。
4. 实际拍代表静态视角，按已约定范围看明显问题；相关接触使用已有检查。
5. 在约定返工范围内定向修正，展示真实结果与尚未验证内容。交付到此结束，等待作者对影视城的意见。

代表视角按本次布局选择，可以包括宗门关系远景、池边冲突方向、反向机位、竹枝/池沿近景和回茅屋方向。它们是取景依据，不是今后每次修改都必须重拍的固定清单。

### 10.4 后续视频阶段的交接

作者允许继续后，镜头制作读取这次已保存的空间与场面决定，补充表演、实际估时和声音。视频生成单元依实时能力拆分，整场时间由剧情决定。

粗剪优先验证“介入与保护是否看懂、身份揭示是否有层次、万剑与声音是否形成反转、结尾日常台词是否有停顿”。实际问题回到对应镜头、动作、声音或布景，不重新跑完整筹备。

## 12 验收方案

### 12.1 代码与业务合同

针对真实断点补回归，不为每个可选字段增加镜像测试。至少覆盖：

1. 作者交付中的节拍、障碍和入出场状态可被下游读取；制片改稿后旧事实不冒充当前事实。
2. 无导演 Skill、无镜头时基础方案可保存；同一次提交方案与镜头可以成功。
3. 人类入口与外部 Agent 入口获得同源决定；建城确实接收相关需求。
4. 修改无关资产或制作约定，不改变当前生成/建城的内容依据；相关变化能被定位。
5. 提示、缺备注、缺部门报告和低评分不阻止草稿或普通制作；真实必需引用、暂停、版本冲突和已知接触失败仍被正确处理。
6. 达到约定范围后不自动启动新生成；再次读取、换会话和换种子不清空工作记录。
7. 分割/修剪时间线不修改叙事镜头；素材替换和音轨定位有明确效果，实际导出与预览一致。
8. 旧作品无新字段仍可读写和导出；当前采用、历史候选、作者锁定及互动固定快照保留。

沿用既有文档、Operator 合同、类型与相关领域回归检查。只在实现触及对应模块时运行相关较重测试，不把全库全场景回归变成每次内容修订的制作步骤。

### 12.2 实际运行与画面

| 场景 | 验证目标 | 不应发生 |
| --- | --- | --- |
| 简单双人对话，无 3D、无 Skill | 读本场上下文，一次提交方案与镜头，正常准备素材 | 要求十二部门填表、先做三维或单独审批基础方案 |
| 青云宗只建城 | 已保存场面要求影响布局；静态近中远景能直接审视布景 | 自动启动视频、以对象数判通过、静态用途强制全场动态 |
| 一处明显穿模 | 具体失败参考不能作为合格输入；有限修正后保留结论 | 换任务清空次数、修改镜头藏问题、阻塞无关场次 |
| 一条审美建议 | 记录并交作者或在约定内处理 | 自动降低分数并不断重生成 |
| 上游局部变化 | 只使相关来源旧检查失效并暂停其依赖；旧候选可看、无关成果可继续使用 | 清空全剧媒体或全量重新检查 |
| 任务未知提交与重接手 | 查询原任务，读取已有安排与成果 | 重新提交相同付费任务、重复完整问卷 |
| 一场带声音的粗剪 | 叙事、实际时间、对白、环境声和切点共同可审 | 用文件可解码或文字齐全声称创作合格 |

真实画面按约定粗审，作者做精审。没有播放的动态、不支持的精细动作和未听审的声音分别注明；不把开发测试中的伪供应商结果作为作品质量证据。

### 12.3 效率验收

在同机同项目样本上记录改造前后结果，不预先编造耗时成绩：

- 简单场次新增强制审批请求数为零，额外模型调用数为零。
- 上下文 GET 触发的渲染、生成、全项目检查次数为零。
- 没有新来源或观察时，自动创作复查与重试次数为零。
- 一次范围内修改只让相关内容进入待核对；不会产生全项目待办洪泛。
- 查看一个场次主要依赖一次上下文读取；媒体和长历史按需展开。
- 同机上下文耗时、返回体积与页面可交互时间记录基线及变化。若显著变慢，优先缩小读取范围和消除重复计算，不能用更多缓存/状态层掩盖无必要工作。
- 普通 Agent 能在约定上限后交付已有结果并继续其他任务；系统不要求把所有提示清零才能完成阶段。

## 13 明确的设计决定

1. 协作以场面和产物为中心，专业角色负责决策视角；不会自动变成十二个独立运行实体。
2. 正常保存、使用和采用承载交接；正式推进须有当前质量检查，不建立用户逐步审批链。
3. 基础导演方案独立于 Skill，简单戏可与镜头一次完成，复杂戏按需增加试验。
4. 实际使用的创作决定进入下游上下文与计划；未知和假设可表达，不能冒充事实。
5. 客观无效动作和已证实不适用的材料在相关入口处理；一般创作建议不成为硬门禁。
6. 粗审范围与返工上限服从项目约定；不自动评价、修复、再评价循环。
7. 复用既有来源、版本、候选、暂停、队列和正式采用，工程改动集中在已证明的断点。
8. 创作验收依赖实际作品，技术检查、Agent 粗审与作者采用分别记录。

实施时先交付 P0 的一条完整普通制作路径，再用 P1 的青云宗静态布景检验协作是否有效。后续剪辑与视频验收在获得对应制作授权后进行。


## 14 实施验证记录

- 人与Agent接口：隔离HTTP验证一次保存需求/事件、资产用途、工作记录、无手动保存标记的场次/单镜/3D增量修改；反复GET不写进度或创建任务。换任务不会清零同范围已用记录，实际生成执行数量另从持久任务读取。
