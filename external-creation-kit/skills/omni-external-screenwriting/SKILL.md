# 外部剧本创作

目标是交付可阅读、可拍摄、可继续修改的剧本，以及不丢正文的结构化文件。先阅读 [共用创作规则](../../shared/creation-rules.md) 和 [交付规范](../../shared/delivery-contract.md)。格式以 `schemas/` 为准，样例在 `examples/last-ferry/`。若这些资料没有随任务提供，先说明缺少哪部分，不假装已读取。

## 进入任务

从用户要求识别这次是讨论方案、设计大纲、写正文还是修订。沿用用户已经确定的方向。影响主角、结局、规模等关键问题未明确时集中提问；次要细节可以提出有说明的假设。讨论或设计阶段可以交付 draft；用户已经授权完整创作时，完成正文、自查和交付，不要求用户逐场批准。

以 `story-bible.json` 维护唯一人物、事实、方法和风格来源。先理解角色此刻想得到什么、知道什么、能做什么，以及阻力来自哪里。人物类型、结构理论和题材惯例是选择项，不能替代行为因果。只执行项目选用的方法，发现方法冲突时说明取舍。

## 创作与修订

- 大纲需要推进和结果，分场需要可见事件。每场明确目的、进入和离开时的状态；对白必须有交流对象与意图，动作能被拍摄或表演。内心说明可作备注，但不能用备注替代戏。
- 检查人物获取信息的来源、时间与空间、道具归属、伤势与行动能力、关系变化、伏笔兑现。允许角色隐瞒或犯错，但要区别角色说法和作品事实。
- 场景长度根据表演、行动和停顿估算。不要用字数证明成片分钟数，也不要为达到场数或时长机械重复相同冲突。
- 改编时区分原作固定事实与用户允许改造的部分；不擅自扩展授权修订范围。修改第十二场时保留其他场的文字、顺序和编号，发现连带矛盾则在说明中给出具体受影响对象。
- 剧本中的分支场次分别维护。两种互斥动作不能写在一段连续正文中等播放器自行理解“如果/否则”。互动条件由 `interactive.json` 控制，剧本场次只说明适用路线并提供该路线的完整正文。
- 沿用场次、人物和正文块编号。编辑同一块保留编号；拆分、合并或新增块使用新编号，显式列出删除项。不得用重新编号掩盖修改范围。

## 交付

先完成内容，再整理成标准文件，不把结构化过程变成第二次缩写。每个 `complete` 场次包含完整 `blocks`；`summary` 不能充当正文。对白使用 `speakerId` 引用人物，动作与对白分别成块。

普通影视作品将 `manifest.files.interactive` 设为 null；如果已有互动设计且本次修改影响它，说明需要复核的节点与状态，不能悄悄使旧图看似有效。多人协作或分轮输出以 `projectId`、`deliveryId`、`baseDeliveryId` 和显式交付范围衔接。

交付前依次检查：人物与事实是否成立、全稿节奏与重复、场次连续性、完整正文及引用、文件与清单一致。具备运行条件时执行离线校验；说明实际检查范围，不声称系统已经导入或媒体已经生成。

若超过一次输出容量，在完整文件边界分批输出，维护同一清单；剩余场次标为未交付，不用摘要或“其余同上”补齐。最终给用户文件列表、完成范围、未决问题和修订说明。
